# 业务测试点评审方法

## 两遍检查

第一遍从来源到清单：需求到底要求哪些性质，相关状态、资金和竞争分支是否有判据。第二遍从每条清单回查来源：条件是否充分、预期是否准确、证据是否足够。避免仅校对格式或顺着作者分类复述。

先独立理解业务目标，再阅读清单如何声称覆盖它。上游结论可以复用，但不能成为免于审查的权威。

## 典型判据错误

| 错误模式 | 评审动作 |
|---|---|
| 弱化目标 | 分拆独立性质，用满足较弱条件但违反完整目标的反例检查；不增仓与不反向分别判断 |
| 擅定产品策略 | 回查超额、拒绝、裁剪、取消和排序规则；无来源改为待决子断言，不选一个“常见行为” |
| 阶段混淆 | 定位受理、生效、订单终态、账务完成；不能拿受理立即断言冻结已释放 |
| 数量口径混淆 | 原量减累计成交、活动剩余、取消量、冻结分别按定义核对；改单后检查基准变化 |
| 时序条件不足 | 说明共享资源和生效顺序，区分已成交与未成交、其他业务贡献和本操作贡献 |
| 重复/幂等误判 | 通知数量、请求次数不等于真实业务次数；检查稳定标识、作用域、异参和保留期来源 |
| 循环证明 | 两个同源查询相同不证明底层正确；需要初始快照、事件/流水和独立公式，缺失时说明盲区 |
| 无依据数值 | 检查费率、公式、单位、精度、舍入和时间阈值的来源；示例不能推广为项目默认 |
| 表面完整 | 类别齐全、条数多、ID 关联不等于关键性质有可判断覆盖 |

发现文档或设计问题，不等于已复现产品故障。没有执行证据时只能评审设计的风险与正确性。

## 数据与边界审查

边界应能隔离规则：非法步长、最小量、余额不足等若同时出现，无法证明具体拒绝原因。可设计分组数据或不同点，不必每个数值复制一条。

检查金额是否用实际成交价、费用是否重复计入、冻结释放是否被当成新增资产、币种/单位是否一致，以及读取是否处于同一业务截面。缺少科目定义不能声明全平台资产总和守恒。

最终完成的金额或数量不应在尚未完成时被强制要求。反过来，状态维度独立不意味着来源明确的跨状态约束失效；公式适用范围不清时指出冲突或待确认边界，不能自行修改其生效条件。

按业务键归组有助追踪，但必须保留并累计所有真实资金/持仓效果。若同一个事件误产生两条真实释放，各条效果都应计入；先按事件键只留一条流水会隐藏真实重复副作用，不能用这种算法证明幂等。

拒绝无副作用只针对不应发生的业务成交、持仓或占用，不能把合法审计记录或幂等记录一概视为失败。

## 并发与恢复审查

确认条件足以制造所声称的竞争：两条请求同时发出不证明它们读取了同一旧状态或进入关键窗口。将控制点作为待准备能力，而不是假定已经有内部注入接口。

“先 A 后 B”与“先 B 后 A”如果允许结果不同，不能作为纯标题重复合并。已生效但响应丢失时，基于原业务标识查状态是设计方向；具体重试语义、结果和去重保证仍依赖来源。

时间目标需要业务起点和结束证据。首次查询看到终态可能晚于实际生效；任意 sleep 不能证明达标。用户明确给出的时限应被使用，不能以“时限不能编造”为理由忽略。

## 缺口、重复与优先级

遗漏需要指出对应规则及要增加的判别能力。不要仅说“补充并发/异常”。合并建议保留条件、不同失效机制和独立证据，明确存续点与旧 ID 的映射。

重复 ID 先按原位置区分；数据完整性问题与语义重复分开报告。即使 ID 冲突也不能删除内容。

严重程度：

- **阻塞性**：当前清单会把关键资金、仓位、权限或终态错误判为通过，或关键预期根本无可决依据。
- **重要**：缺少相关竞争、恢复、边界或独立核对，主链路的部分判据仍可继续。
- **一般**：命名、组织或不影响当前判定的完善。

这是评审意见严重程度，不等于用例 P0/P1，也不是已发生生产事故。给优先级建议时说明业务后果及本次变更关系，避免所有点都最高级。

## 仅有测试点时

可以检查内部矛盾、同义重复、数据或观察要求是否自洽；无法核实来源的预期标“业务依据待核对”。不要仅凭通用交易知识补出项目约定，也不要直接认定全部错误。

业务覆盖、规则准确性和执行准备分别给结论。局部缺口只阻塞相关分支，不要求用户在继续任何工作前补齐所有资料。
