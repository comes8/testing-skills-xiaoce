# 评审输出与修订约定

按用户要求交付意见、差异或修订清单。默认先给范围与结论，再列具体意见；如果只要求问题，省去完整改写。

## 意见字段

| 字段 | 语义 |
|---|---|
| REV 编号 | 稳定评审意见 ID，增量复审沿用 |
| 定位 | TP ID 及必要原序号/段落，或缺失覆盖所对应的需求/规则 |
| 类型与严重程度 | 错误预期、漏测、依据缺失、数据/证据不足、重复/ID 冲突等；阻塞性/重要/一般 |
| 依据与后果 | 原始来源及位置、为什么可能误判、影响哪些分支 |
| 修改建议 | 可确定的修订、需新增的性质或仍需项目决策的部分 |

缺少实际运行不能报告“系统有缺陷”；存在多种未定策略不能用“任选其一均通过”隐藏规则缺口。

## 修订记录

用户要求修订时，按修改、新增、保留、合并/废弃建议给出差异。保留原 ID 与来源，重复 ID 用原序号定位；需要分配新 ID 时给出映射，不能悄悄让两个不同点共享一个结果。

新增/修改后的点至少包含目标、条件/触发、预期及依据、核对方式和待确认部分。清单有用的观察或时序不能因合并而丢失。

仅给建议时清楚标为建议稿，不声称原文件或平台数据已修改。用户明确要求修订文档时在当前授权范围执行，但不扩展成平台写入或业务执行。

## 结论的三个维度

1. **设计判断**：可继续展开 / 局部修订后继续 / 关键判据存在阻塞问题，附具体依据。
2. **范围与覆盖**：实际评审了什么、哪些未覆盖或依据不足，不伪造覆盖率。
3. **执行准备**：需要的数据、关联证据和时序能力；未执行不写通过/失败。

如果没有原始来源，应明确“内部一致性可评审，业务预期及覆盖待核对”。如果用户只指定一个点，则给局部判断，不能宣称整批清单通过。

## 与上游衔接

保留已有 SRC/REQ/RUL/MOD/INV/ISS/TP 编号，没有专门模型也可以直接查原始资料。评审不要求安装其他技能；它是业务设计检查，不附带平台 Schema 适配、自动化执行或交易授权。
