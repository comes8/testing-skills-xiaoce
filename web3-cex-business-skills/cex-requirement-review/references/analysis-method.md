# 需求分析与评审方法

## 读取路径

- 首次分析：输入基线 → 业务与实现映射 → 覆盖方向 → 验收依据。
- 评审补全：先读现有材料和已有问题，验证其依据，再补充遗漏与冲突。
- 增量任务：先定位改动，复用未变化结论；不要重新编号或重新展开全部报告。

## 输入基线

给材料标记来源 ID。优先使用资料已有版本；没有时写“未标版本”，不要用文件修改时间冒充业务版本。网页记录产品和访问日期。来源位置应足够让研发或产品复查。

区分四种信息：用户希望的目标行为、已批准的项目约定、现有实现行为、历史缺陷的复现事实。它们可能相互矛盾。不能因为代码已经这样写，就认定需求不需要调整；也不能把一份草案当成现有实现已满足。

最小必要输入包括需求或变更描述与实际产品范围。账户模式、数量单位、初始数据、接口和技术方案按当前分析所需补充。缺少某项只阻塞依赖它的结论。

## 业务与技术影响映射

按实际资料绘制相关链路，不要求项目采用特定架构：

| 观察位置 | 研发视角要核对的变化 | 测试开发需要保留的依据 |
|---|---|---|
| 用户/接口入口 | 参数语义、权限、兼容性、请求去重 | 输入约束、身份与业务标识 |
| 业务校验 | 校验发生时点、判断使用的状态、拒绝是否有副作用 | 校验前后快照和拒绝分支 |
| 核心处理 | 订单/仓位/余额变化，原子边界，竞争对象 | 状态转移、数量关系、不变量 |
| 持久化/事件 | 若使用存储或消息，谁写入、谁消费、失败如何恢复 | 可读取字段、关联键、重放与去重范围 |
| 查询/推送/展示 | 数据生产者、延迟语义、增量和快照对应关系 | 能关联同一业务对象的观察源 |
| 配置/发布 | 生效对象、生效时点、在途业务、回滚 | 新旧规则适用边界和存量数据行为 |

仅提取能影响测试的实现事实，不把分析变成未经请求的重构方案。记录实际读取的接口、函数或字段；未读取的内容写“需研发核对”。

## 场景推导

从一个明确规则出发，沿触发条件、状态、数据、时序和依赖变化推导场景。每个候选场景说明它检验什么业务性质，避免把枚举值排列当成覆盖充分。

1. **主业务结果**：谁在何种前提下触发，哪个对象发生什么变化，下游需要完成什么。将多条件目标拆成独立约束，为每个约束找能推翻它的反例；检查通过某个较弱约束但仍违背原目标的情况。
2. **允许与拒绝边界**：变动一个有效性条件，核对正确拒绝及副作用；权限和资产归属单独考虑。
3. **部分结果与状态转移**：完成一部分后取消、重试或发生其他业务，是否仍满足数量和资金关系。
4. **竞争与事件顺序**：标出真正竞争的资源和操作，分别分析先后发生与并发窗口；需要控制时序时说明控制点。
5. **依赖与恢复**：区分提交前失败、提交成功响应丢失、部分下游完成；据此分析查询、补偿和重试。
6. **一致性与观察**：说明订单、成交、仓位、资金、事件或展示之间如何按业务键关联，何时应收敛。
7. **变更兼容**：当规则改变，明确在途对象、历史记录、客户端和配置分别采用哪个版本。

组合选择依据：资金风险、状态交叉、竞争资源、变更触达和历史缺陷。对未触达的产品或功能不强行补入。对于重要组合，说明为什么不能被单一参数边界替代。

## 风险和阻塞范围

风险写成“条件/触发 → 失效行为 → 业务后果”，例如“响应丢失后无业务标识查询 → 重试创建第二个业务 → 可能重复扣款”。说明这是待核实风险还是已发现事实。

- **阻塞性**：规则冲突或缺失会导致目标行为、资金预期、权限边界或关键终态无法判定。
- **重要**：影响异常、竞争、恢复或兼容分支，主链路已有足够规则。
- **一般**：表述、可读性或不影响当前关键分支的完善项。

这是评审问题严重程度，不等同于测试用例 P0/P1，也不等同于已发生缺陷。每个问题写明“阻塞哪个结论”和“哪些部分仍可继续”。

## 验收与独立证据

验收条件采用可观察表达，避免“正确处理”“稳定可靠”“实时同步”等无判定标准的句子。

| 需要确认的结果 | 建议核对方式 | 不能直接得出的结论 |
|---|---|---|
| 请求被受理 | 请求业务标识、返回状态、对象查询 | 受理不等于已完成 |
| 成交发生且数量正确 | 同一订单对应的成交明细、累计与剩余数量 | 两条通知不等于两笔成交 |
| 仓位与余额正确 | 固定初始快照、关联成交/流水、已确认公式 | 单一余额返回值不证明结算正确 |
| 异步链路收敛 | 同一业务键跨观察源核对，明确收敛条件与时限来源 | 任意固定睡眠不证明时序正确 |
| 拒绝无业务副作用 | 明确项目允许的审计记录，对比订单/资金等业务状态 | 不能要求所有数据库完全没有写入 |
| 恢复后业务不重复 | 稳定业务标识、终态、流水与副作用次数 | HTTP 请求数不等于业务执行次数 |

优先选择不完全依赖同一读模型的证据；无法独立核对时说明盲区。分析阶段可以建议测试接缝、时钟控制、价格输入或事件观察点，不能声称这些能力已经存在。

对金额必须标清币种、数量单位、合约乘数、费率单位和舍入时点。资料不足时给公式需要的变量，不自行填入默认费率或保证金档位。

## 补充需求与持续修订

补充内容标为建议，说明解决哪个问题。若存在多个合理方案，列出业务差异及需决策内容，不代替项目负责人拍板。

对新补充先定位它解决的旧问题，保持问题 ID。修订意见与修订条款分开；没有新来源时不能把“待确认”改为“已明确”。用户只要求某个问题或分支时，交付相应差异即可。

没有明确要求时，停在需求分析、评审及验收依据。测试点、完整用例、平台写入和真实请求均是后续任务，不由本 Skill 自动触发。
