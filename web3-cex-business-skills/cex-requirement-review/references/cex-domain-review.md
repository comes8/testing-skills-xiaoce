# CEX 业务审查维度

本文件提供提问和推导方法，不定义任何交易所的固定产品规则。只加载与当前需求有关的章节。每个候选维度都需要落到本项目来源、待确认问题或合理的不适用说明。

## 1. 先识别产品与能力

确认交易产品、合约单位及结算方式、账户/持仓/保证金模式、委托能力、行情来源和配置版本。不要默认所有产品支持相同订单类型，或所有账户都支持同样的模式组合。

新旧规则混用时，核对在途订单与存量仓位适用哪一版。外部资料只能说明相应平台的行为；项目没有确认映射前，作为候选参考而非验收预期。

## 2. 现货订单与撮合

| 相关变化 | 核对问题与场景方向 |
|---|---|
| 下单校验 | 交易状态、账户权限、可用资产、价格和数量单位、最小金额、精度与校验顺序是否明确？拒绝是否产生冻结或订单？ |
| 撮合规则 | 优先级、成交价、同价规则、自成交处理与订单类型的适用条件是什么？不要默认一套全市场通用规则。 |
| 部分成交 | 累计成交、剩余量、剩余冻结、手续费及后续撤改单分别如何变化？累计口径与单笔口径是否混淆？ |
| 有效期和流动性 | 项目支持的 IOC/FOK/Post Only 等分别怎样处理可成交量和价格？FOK 的判断与执行边界如何保证目标语义？ |
| 撤单/改单 | 受理、执行、查询分别说明什么？与成交竞争有哪些合法终态？改单是否保留优先级、改变冻结或生成新订单标识？ |
| 查询和事件 | 订单、成交、深度、资产推送如何按 ID/序列核对？重复通知是否会被误当成重复成交？ |

对于并发撤单，先分析“成交先完成”“撤单先完成”“撤单期间又部分成交”等相关顺序，再提出需要控制的事件点。数量与资金核对使用最终成交明细和规则，不仅检查订单状态名称。

## 3. 合约账户、委托与仓位

| 维度 | 应分析的规则与相互作用 |
|---|---|
| 产品和模式 | 线性/反向、永续/交割，数量是张/币/名义金额？账户、持仓、保证金模式有哪些合法组合？切换受哪些在途订单/仓位限制？ |
| 普通和条件委托 | 是否支持只减仓、全平、条件委托、止盈止损等？触发价格来源、触发时校验及与普通委托的关系是什么？ |
| 仓位生命周期 | 开仓、加仓、减仓、全平、反向交易时，方向、数量、均价、已实现/未实现盈亏如何变动？ |
| 可平数量 | 当前仓位、已挂减仓委托、其他成交及风控操作之间如何分配？判断时点在提交、触发还是实际执行？ |
| 挂单与仓位关系 | 挂单后仓位被其他业务改变，旧委托是拒绝、裁剪、取消还是保留？需要项目明确，不能从习惯推断。 |
| 成交和费用 | 单笔与累计、手续费币种、合约乘数、价格与金额精度、舍入时点、maker/taker 判定是否明确？ |

### 只减仓需求的推导方法

先确认“只能减少当前方向仓位”和“不能形成反向仓位”是否为项目明确目标，分别检查其成立条件，不能用“不反向”代替“不增仓”。无其他仓位事件时，合法的正数量减仓成交应使原方向绝对张数减少，且不跨零形成反向仓位；未成交不能要求张数已经减少。例如多仓 5 张变成多仓 7 张虽然没有反向，仍违反只能减仓；空头持仓也要核对同方向增仓的反例。有其他开平仓事件时，按本委托的成交归因检查，不能用总仓位净变化掩盖错误加仓，也不能把其他业务合法加仓误报成本委托违规。

再按实际范围分析：

- 无仓位、减仓量小于/等于/大于可平数量、非法方向和精度边界。
- 多笔减仓委托共同竞争仓位；创建、触发与成交阶段检查是否一致。
- 部分成交后撤单/改单，或其他成交先将仓位减小/归零。
- 用户平仓、止盈止损与强平竞争同一仓位；哪些路径实际存在且触达本次变更。
- 委托提交超时、重试与重复事件；按原业务标识查询最终状态，核对真实成交和仓位。
- 仓位数量、已实现盈亏、费用、保证金释放及对应流水是否一致。

超额处理、并发仲裁、模式兼容和冻结策略均需本项目来源。缺失时输出待确认问题，不把某个平台行为写成统一答案。

## 4. 合约保证金、价格和风险处置

| 维度 | 核对问题与场景方向 |
|---|---|
| 杠杆与保证金 | 杠杆和风险档位变化如何影响初始/维持保证金、挂单占用和可提额度？逐仓/全仓计算边界是什么？ |
| 价格与估值 | 最新价、指数价、标记价分别用于什么？价格缺失、过期、跳变时，委托、估值和风控如何处理？ |
| 盈亏 | 线性和反向公式、单位、均价、费用归属与舍入是否有来源？哪些结果能独立计算？ |
| 资金费 | 哪些仓位参与、在哪个时点取快照、金额和方向如何计算、余额不足怎么处理、与其他结算如何排序？ |
| 交割 | 最后交易时点、在途订单处理、结算价格来源、费用与仓位归零规则是否明确？仅对相关产品展开。 |
| 强平 | 阈值、风险档位、撤单和减仓顺序、部分处置/接管、并发仲裁及完成条件是什么？ |
| 后续资金处置 | 项目是否支持保险基金、ADL 等？触发、排序、费用/损益分配、流水和通知如何核对？不存在的机制不补入需求。 |

只在改动触达相关计算或处置链时展开对应组合。价格、资金费、强平、平仓相互影响的场景应标明事件顺序和账务截面，避免将不同时点数据直接比较。

## 5. 资金账务与链上边界

| 维度 | 核对问题与场景方向 |
|---|---|
| 冻结与结算 | 可用、冻结、余额、权益的项目定义是什么？谁冻结、何时消费/释放，部分完成和拒绝如何处理？ |
| 划转 | 转出、转入与流水的原子性或补偿语义如何定义？唯一业务标识覆盖多长时间、哪些字段？ |
| 手续费 | 费率来源、生效时点、币种、折扣/返佣、maker/taker、舍入及退款规则是什么？ |
| 对账 | 订单、成交、仓位和流水有哪些关联键？余额变化由哪些已分类事件解释？是否允许未结算中间态？ |
| 充值/提现 | 若需求涉及链上，确认链与资产标识、确认与回滚政策、事件唯一性、手续费和失败补偿。确认数不设通用默认值。 |

不要在未定义账户分类、外部流入流出及费用归属时宣称“所有余额总和守恒”。先定义业务范围和资金科目，再核对增减关系。成功响应、链上回执和平台账务入账可能代表不同阶段，需要项目约定。

## 6. 行情、异步事件与查询

确认快照和增量、序列号范围、重复/缺口/乱序语义、重连补偿以及私有事件与查询的一致性。只对需求实际涉及的协议作分析。

说明哪个事件代表受理、哪个代表业务终态、哪个说明资金完成。查询和推送来自同一读模型时，不把二者一致当成完整独立证据。金额与数量使用相同业务截面；缺少收敛目标时提出待确认问题。

## 7. 权限、配置、兼容与技术可验证性

- 账户、子账户、API 权限、产品状态和风控限制是否在正确边界生效？只评审需求触达的权限。
- 配置变动适用于新单、在途订单还是存量仓位？缓存或消费者尚未更新时的合法行为是什么？
- 旧字段、旧客户端、历史数据和回滚后状态如何处理？没有相关变更不强加迁移工作。
- 如提供实现资料，检查原子更新、幂等键、事件消费和读模型更新；未提供时将这些列为研发核对点。
- 说明需要哪种数据准备、事件控制或观察能力；不要假定测试环境可以直接改数据库或触发真实强平。
