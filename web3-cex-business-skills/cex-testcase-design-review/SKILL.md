# CEX 业务用例设计与评审

把测试目标落实到另一个人能够理解、准备和逐步检查的用例；评审时既核对业务预期，也检查数据、动作、观察和依赖是否真的足以支持结论。

先选择生成、评审或增量修订模式。读 [用例设计方法](references/case-design-method.md) 与 [输出与交接](references/output-contract.md)；评审已有用例时再读 [用例评审方法](references/case-review-method.md)。用户只要意见则不重写清单，只展开指定点或变体时保持该范围。

## 1. 建立规则与用例基线

读取原始需求、测试点、模型、已有用例及准备条件，保留来源、版本、产品/账户模式和已有 ID。上游测试点不是免检答案；错误或待确认预期不能因展开成步骤而变成规则。

区分材料明示、实现观察、推导、建议与待确认。没有专门模型或测试点时可从足够明确的原始资料直接设计，不强制先安装其他 Skill。缺少决定性规则时给局部受阻，不编造错误码、费率、接口、时限或仲裁策略。

## 2. 将目标拆成有判别力的用例

每例对应一个连贯业务场景，允许多个观察共同证明它。独立的竞争顺序、模式或阶段变体应单列用例或子用例并分别留证，不能只执行一个变体就将整组判通过。

保留原 TC 与 TP 映射；一例可覆盖多个相关点，同一点也可有多个变体。编号冲突用原位置定位并给映射，不静默覆盖、重编号或删除不同场景。

选择能区分正确与错误实现的初态，不用相同终值掩盖错误过程。例如全量替换需要新快照缺席的旧档；不同竞争顺序需要控制真正生效点，不仅同时发请求。

## 3. 写清数据与前置条件

给出角色/账户和产品引用、规则版本、初始订单/仓位/资金快照、所需关联键、隔离范围以及已经存在的控制/观察能力。参数合法性有缺口时列待准备数据，不能把“账户准备好”作为完整前置。

优先复用项目夹具和授权数据能力；没有真实接口时用明确的业务操作描述，不发明 URL、API ID 或内部工具。创建的新数据引用是设计变量，不冒充已创建的真实对象。

说明每例独立准备还是依赖前例；有依赖时明确产物、失败阻塞和恢复方式，不让用例暗中共享上次剩余仓位。不可逆业务不靠删账、改余额或撤回真实成交来清理；只规划来源允许的隔离夹具清理，并先保留证据。

## 4. 步骤与预期逐一对应

每步给具体动作或观察，以及该步唯一对应的预期描述；描述可包含证明同一性质的多个相关观察值。不要把全部预期集中到最后，也不把不可同时成立的不同分支塞成任选结果。

步骤按状态依赖排序，明确提取哪个实际关联标识供后续使用。受理、执行生效、订单终态、资金完成分别定位。数值预期带单位、业务截面、公式来源及精确计算，不把完成值套到处理中。

异步等待使用来源定义的完成条件和窗口；有时限时记录实际起点/终点及误差来源，不能用首次轮询加固定 sleep 证明达标。未给时限时列待确认，不写无限轮询或任意秒数后必成功。

竞争/恢复步骤写明需安排的生效顺序、处理窗口和观察证据。重复在处理中到达时，原业务可能正常推进，不能一律要求余额不变；完成后重复与处理中的判据应分开。控制能力未知则标准备缺口，不伪造已经可执行。

## 5. 独立核对与可执行性审查

用初始快照、真实成交/流水和已确认公式核对结果，金额采用 Decimal 或最小单位整数；同源查询相等或被测返回值自证不足。整数示例不证明资产账务精度。

通知可归组，真实资金/仓位效果必须完整保留并按账户/科目解释；不能按同 ID 删除真实重复效果，也不按合法分录行数判断重复。最终净额正确仍需检查来源禁止的过程。

按 [评审方法](references/case-review-method.md) 检查每步是否可准备、可操作、可观察、可归因；规则缺口、数据/能力缺口和执行结果分开。已有报告的“通过”只有在版本、环境、数据和执行证据匹配时才有相应含义，不能继承为新用例已执行。

## 6. 交付与边界

交付用例或评审差异、TP/规则映射、就绪度、待确认和准备项。用户只要局部修改时保留未变内容，给修改原因，不重造全套资产。

Markdown 或 JSON 仅是交付形式；对接 N-Tester/XMind 时核对具体 Schema，业务编号不自动等于平台数据库 ID。当前不导出脚本、不调用业务、不注册平台或安装技能；需要执行/导出时沿用用户指定平台和后续明确任务，不另建框架。
