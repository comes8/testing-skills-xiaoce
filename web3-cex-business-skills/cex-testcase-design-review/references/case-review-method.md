# 用例评审方法

先从原始需求/测试点反查该例应该证明什么，再沿每一步检查条件、动作与预期。不要仅校对文字或假定已评审过的测试点必然正确。

## 逐例检查

| 方向 | 要发现的问题 |
|---|---|
| 规则和版本 | 旧版预期被用于新规则、建议被当事实、费率/精度/时限无来源、模式不适用 |
| 数据与前置 | 参数不合法、多个非法条件叠加、隐含前例依赖、夹具缺乏判别力、观察能力被假定存在 |
| 步骤顺序 | 未成交提前检查仓位/费用、受理即当终态、没有安排声称的竞争窗口、先清理再取证 |
| 预期关系 | 数量口径混淆、实际价与限价混用、保证金重分类当收入、费用重复计、最终值套处理中 |
| 独立证据 | 同源查询循环证明、按ID丢弃真实重复效果、按行数误判合法多分录、跨截面读值硬拼公式 |
| 异步/异常 | sleep代替SLA证据、无限轮询、无依据重试/退款策略、局部缺口被扩大为全局无法设计 |
| 编号和维护 | 同ID不同变体被覆盖、不同事件顺序误合并、整表重编、只执行一个子例就判全部通过 |
| 执行结果 | 没有证据就写通过、继承不匹配版本的历史结果、把可设计当环境已就绪 |

问题定位到用例与步骤/原序号，给依据、业务后果、严重程度及可行修订。没有真实运行不能报告已复现软件缺陷。

## 修订边界

用户只要意见就不重写全例；要求修订时，保留有效前置、步骤、来源及ID，修改真正有问题的部分。重复ID用原位置区分，给子用例或新ID的显式映射，不悄悄丢一个分支。

多种未定策略不能合成“任一结果皆可”。已明确性质继续检查，待定响应/余单/金额与环境能力分别标记；补充问题要说明影响哪一步。

对只评指定用例的请求，未审范围明确列为未审，不因其他清单也有可疑文字就扩展成全部评审，更不能宣称整套通过。

## 结论

分别说明业务设计是否可继续、执行准备是否齐全、实际执行是否有证据。关键判据错误应先修，普通表达问题不阻塞所有设计。用例评审结论不是需求批准或发版许可。
