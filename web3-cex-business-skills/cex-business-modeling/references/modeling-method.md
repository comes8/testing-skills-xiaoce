# 建模方法

## 范围选择

链路模式回答“业务从哪里到哪里、分支与上下游是什么”；规则/状态模式回答“何时允许改变、改变什么、哪些结果禁止”；增量模式只更新受新规则影响的节点和关系。无需每次同时绘制所有视图。

采用业务可理解的对象和动作，不要求项目具备某种微服务架构。没有真实接口时可写“查询订单的能力待核对”，不能虚构 URL 或 API ID。

## 对象与独立状态维度

| 对象 | 建模时要区分的内容 |
|---|---|
| 订单/委托 | 提交、受理、生效、成交、取消、失效的语义；实际状态枚举以项目为准 |
| 成交 | 一次真实执行与其通知；单笔、累计、撤销或更正事件的项目语义 |
| 仓位 | 方向、数量、均价、所属产品/账户/保证金边界，变化归因到哪个事件 |
| 资金 | 可用、冻结、余额/权益与处理阶段；哪些定义可直接相加需要来源 |
| 账务 | 业务标识、借贷/收付科目或已定义流水类型、记账与结算阶段 |
| 行情/推送 | 生产来源、序列范围、快照/增量、重复通知与缺口恢复 |

不是每次都建全部对象。一个状态表不足以承载所有生命周期：例如订单已经取消，资金可仍处于项目允许的处理中状态。把这一组合写成两个维度及它们的合法关系，不增加一个未经定义的订单枚举掩盖差异。

## 节点与转移的最小信息

节点：对象、触发、条件、动作、业务生效位置、效果、后继及观察点。

转移：原状态 → 事件/守卫 → 新状态，附数量/资金效果、关联规则及未知分支。对“失败”进一步区分未受理、已受理结果未知、业务拒绝和部分下游完成，只有资料支持的状态才能固定。

把跨模块顺序分为：资料承诺的顺序、实现观察到的顺序、仅为推演设定的事件序列。后者不能升级为真实系统保证。未明确的事务边界、消息投递保证、锁策略或时间窗口列问题即可。

## 数量和金额建模

先定义每个变量对应的业务口径。例如在明确没有改单、更正、额外成交的固定订单截面，可建立原量、累计成交、活动剩余和取消量之间的关系；具体等式依赖项目定义。撤单后活动剩余可以归零，而“原量减累计成交”仍可能表示被取消的未成交数量。若公式未说明阶段而另一条规则允许异步处理，应指出适用范围可能不明确，提出分阶段的建议解释，不能把解释冒充既定约束或强行选一个来源覆盖另一个。

金额按已定义账户和币种分开。固定初始状态、真实成交、费用及其他资金事件后，再推导可用/冻结或余额变化。先识别成交占用、释放和费用是否重复计入，不能把“释放冻结”同时当成新增外部资产。

合成示例数字仅适用于示例。线上项目必须确认合约乘数、金额与数量单位、币种、手续费、盈亏和保证金公式、精度及舍入时点。资料足够时独立计算，资料不足时记录无法求值的变量与受阻结果。

## 目标、不变量和反例

将自然语言复合目标拆成多个独立性质，分别寻找违反它的结果。只减仓不因“没有反向”就成立：同方向持仓增加仍然违反目标。要核对多头、空头和无仓位的适用条件，不能混淆单向持仓模式与仅允许多头交易。

并发下优先按实际业务生效顺序和事件归因核对。其他业务合法加仓可能让全局净仓位增加，不能据此直接判本委托错误；也不能让其他平仓掩盖本委托错误加仓。

拒绝无副作用应明确“哪些业务副作用不允许”，不要要求没有审计、幂等记录或任何数据库写入。

## 时序、失败与恢复

对真正竞争的资源列相关顺序：A 先、B 先和存在交错的窗口；每个顺序注明已知结果与待定结果。不要将所有操作任意组合。

超时后保持业务标识与状态确认路径；具体重试结果、去重作用域、异参冲突和保留期限依赖项目来源。重复消息、真实重复执行、重复入账是不同问题。

当两个消费者独立完成时，描述合法中间态、完成判据、失败补偿或重放边界。没有资料时不能默认 exactly-once、分布式事务或某种补偿顺序。最终结算应有的全部金额只在满足完成前提时固定；处理中仍须检查已明确的不变量，但不能要求尚未发生的全部释放已经完成。

按业务标识归组可用于追踪通知与效果的对应关系；真实成交、持仓和资金副作用必须完整保留并累计。不能先按重复 ID 抹去实际重复扣款/释放，再用去重后结果证明没有重复执行。

有时间 SLA 时需要实际起点和结束时间证据。若只能轮询，说明时间误差和能证明的范围；没有时限时不给任意等待值。

## 开发与测开交接

有代码和技术资料时，只记录实际查到的校验点、读写对象、事件和配置。把需研发确认的并发控制、数据一致性和恢复保证单列；这是分析依赖，不是擅自指定实现方案。

建议最小的可验证接缝：初始化对象、触发业务事件、控制顺序、读取关联结果。区分测试设计希望具备的能力与当前环境已证明具备的能力。为后续测试点给出可核对性质，不自动创建数据、改库或调用真实业务。
