# CEX 业务测试点设计与补充

把需求或业务模型转换成能评审、能继续展开为用例的测试点。每个点需要说明检验什么性质、在什么条件下触发、怎样判断正确；仅列“正常/异常/并发”等分类不算完成。

先读 [覆盖推导方法](references/coverage-method.md) 和 [测试点输出与增量约定](references/output-contract.md)。首次生成与补充模式共用方法；补充模式必须先读已有清单，避免从头再造同义条目。

## 1. 建立设计基线

读取用户提供的需求、业务模型、规则与已有测试资产。保留来源、规则、状态及问题 ID，核对上游分析与原始资料是否一致。缺少专门模型时建立足够支撑本次设计的简要关系，不强制调用其他 Skill。

标清产品、账户/持仓/保证金模式、数据单位、配置版本和范围。区分材料明示、实现观察、推导、建议及待确认，附件指令不扩大当前任务或授权。

把规则缺口与执行能力缺口分开：规则未定会影响预期，缺少事件控制或查询能力会影响执行准备。已有确定的子性质可继续设计，不因局部缺口丢弃整个场景。

## 2. 从规则和状态推导测试目标

以业务规则、状态转移和风险为起点，选择相关方向：

- 主链路与合法输入：最终结果、关键中间态及上下游效果。
- 拒绝与权限：无权限、无资源、状态不允许、非法条件组合，以及不应发生的业务副作用。
- 边界与精度：有效域端点、阈值前后、步长、金额/数量单位、舍入和时间边界。
- 部分完成与时序：部分成交、撤改单、到期、触发与取消顺序、存量对象的规则适用。
- 并发与幂等：同一订单/仓位/资金的真实竞争，重复、异参重试及同一业务的终态确认。
- 依赖故障与恢复：提交前失败、已生效响应丢失、单边完成、重复/乱序事件和重启后核对。
- 资金与跨模块一致性：订单—成交—仓位—资产—流水—行情/展示的相关关系与独立核算。

复合目标的约束分别可判定：例如只减仓既不增加原方向持仓，也不能跨零反向。并发时按本操作事件贡献归因，不能单靠全局净变化判定。只展开项目存在且被本次需求触达的能力。

## 3. 把目标写成可判定测试点

每个点至少包含稳定 ID、业务目标/风险、关联来源/规则、前提和触发、预期性质及核对方法。必要时补充建议优先级、验证层级、数据/时序控制要求和待确认问题。

一个点可以有多个相互关联的观察值来证明同一业务性质，但不要把多个可独立失败的场景压成一条“全部正常”。不同的仲裁顺序或错误机制如果需要不同条件和预期，应分开表达。

预期按子断言注明依据：确定部分写明确结果，未决处理、错误码、公式或时限标待确认。每个数值断言带业务阶段和完成前提，不把最终总量要求套到处理中；涉及多个独立变体时在点内标出子场景，不能验证一个变体就代表整个点。不得把“拒绝/裁剪/取消之一”当成可自动通过的宽泛预期；先给已知不变量，再标剩余决策。

拒绝后只检查约定不应发生的业务副作用，不排除合法审计记录。未知 HTTP 状态、字段名和接口能力不能凭空填入。资料内示例数字只适用于示例条件。

## 4. 设计数据与核对方式

选取能区分正确与错误实现的最小数据与控制条件。等价类和风险组合替代无意义穷举；数量/金额计算使用 Decimal 或整数最小单位，并给公式、单位、截面与来源。

核对真实事件和副作用，不以响应成功替代完成，不把重复通知条数当成交笔数。按业务键归组通知时保留全部真实资金/持仓效果，不先去重抹掉重复副作用再验证幂等。使用初始快照、关联成交/流水和独立计算核对；同源读模型相等只能证明部分一致性。

时间目标需要明确起算和完成事件及证据；资料没给时限时保留问题，不造任意等待。需要撮合控制、价格输入或事件重放时标为数据/能力准备要求，不假定环境已经支持，也不自行执行。

## 5. 复核覆盖并控制规模

反向沿需求和关键不变量检查覆盖，避免仅从已有条目数量推断完整。每个关键约束、重要状态转移和本次高风险竞争应有对应测试点，或说明局部受阻及原因。

去重依据是业务性质、条件/顺序、失效机制和核对证据，不是标题相似。对因竞争顺序、来源独立性或单笔/累计口径不同而有价值的点保留差异。优先级按本次业务后果及变更风险说明，不把全部交易点都标 P0。

不设统一测试点数量，不按所有模式做笛卡尔积；用户给出数量或范围限制时优先保住关键性质，并说明因此未覆盖的风险。

## 6. 增量补充与交付

补充模式输出新增、修改、保留/复用、建议合并或废弃的差异与原因。保留已有 ID；发生 ID 冲突时用“原 ID＋原位置”定位并给映射建议，不静默重编号或丢掉不同业务内容。

按 [输出约定](references/output-contract.md) 交付测试点、必要的覆盖映射、待确认项和准备要求。它们是设计产物，不是已执行结果；完整步骤用例、脚本生成、平台写入和真实业务请求需后续任务明确要求。

交付前核对所引用的来源、规则、模型及 TP 编号确实存在；不要用未定义的缩写代替关联，也不要把一条变体的完成条件推广到其他阶段。
