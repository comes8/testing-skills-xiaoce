# 覆盖推导方法

## 规则驱动的推导顺序

1. 列本次业务目标、条件、状态转移、关键数量/金额关系和来源。
2. 将复合目标拆成能独立违反的性质，为每个性质找具体反例。
3. 选择相关数据、时序、竞争和依赖变化，说明每种变化为什么可能破坏该性质。
4. 明确可观察结果、独立核对方式及尚未决策的部分。
5. 回查每个关键来源是否有覆盖或清楚的受阻说明。

分类只是辅助视角。同一条部分成交后撤单测试点可以同时属于状态、资金和异步一致性，不要为分类齐全复制三遍。

## 方向与判定

| 方向 | 有价值的设计方式 | 常见无效写法 |
|---|---|---|
| 正向 | 给合法条件、触发、状态/数量结果与证据 | “正常下单成功”但不说明成功阶段 |
| 反向/权限 | 改变具体允许条件，核对拒绝及业务副作用 | 未给规则却编造错误码，或要求没有任何数据库记录 |
| 边界 | 依据单位、精度和有效域选边界内外值，隔离不同失败原因 | 用二进制浮点凑金额，或多个非法条件叠加导致不能归因 |
| 状态 | 遍历相关允许转移与禁止转移，区分对象生命周期 | 撤单后把活动剩余、原量减累计成交、冻结都设为零 |
| 时序/并发 | 固定竞争资源和可控制事件点，分别描述必要先后顺序 | “并发 100 次”却不说明争用什么和错在哪里 |
| 幂等 | 依据业务键、作用域、保留期和重复副作用判定 | HTTP 重试次数等同真实成交数 |
| 异常恢复 | 按失败发生在提交前/后、单边完成等阶段设计恢复核对 | 所有超时一律失败，再生成新业务 ID 盲重试 |
| 一致性 | 固定业务截面，按关联键核对事件、资金变化与独立公式 | 两个同源查询相同就宣称账务正确 |
| 配置/兼容 | 只检查本次变更触达的在途对象、参数版本和旧入口 | 无关需求也展开全部迁移或所有账户模式 |

## 场景粒度

一个测试点描述一个可讨论的业务风险或性质，可以联查订单、仓位、资产和流水。核对来源多不等于必须拆多条。

如果条件、预期、事件顺序或失败定位相互独立，应分开；若只换了同等风险数据，可放进等价类集合。为了简洁在同一 TP 下保留变体时，用子场景标签标出条件和判据，后续应逐变体留证，不能单跑一个变体判整点通过。不要用“支持各种异常”代替具体失效机制，也不要把每个字段的每个值变成独立业务点。

在并发模型中，若 A 先和 B 先允许不同终态，应分别说明。未知仲裁策略时只固定已有业务不变量，未决终态列问题，不能把所有可能结果都列成可接受以回避判断。

## 关键交易推导

- 现货：订单原量、累计成交、活动剩余/取消量、资金消费与释放，按项目定义核对；改单改变基准时更新关系。
- 合约：只减仓应分别检查不增仓、不反向、未成交不提前计减仓，及不同事件对同一仓位的归因。超额处理需项目规则。
- 资金：初始快照加已分类事件解释期末变化，明确币种、费用和舍入；不能把解冻当外部新增资产。
- 行情/私有事件：序列范围、重复/缺口与查询截面要有来源；不能按通知条数推算业务次数。

以上是推导方向，不定义平台固定行为。已批准规则、草案明示、逻辑推导和实现观察需要保留区别。

## 预期与受阻分支

规则明确且可给判据的部分可继续设计，即使执行环境暂不具备观测能力。规则未定时，标明缺少什么和哪些断言不能固定，避免给宽泛的“正常处理”。

示例：已知不能增加仓位，但超额策略未定时，可以设计检验“不增仓”的目标；不能硬写超额请求必须拒绝、自动裁剪或一定取消。将可判定性质与待决响应/终态分开。

数据准备和观察能力是另一维度：哪怕预期完全明确，缺少初始快照、业务关联标识或受控时序，也不能说该点已经具备执行条件。

处理中和完成后应分别给判据：最终释放 30 个金额单位，不代表尚未释放的处理中截面也必须已经释放 30。只有来源明确的中间状态关系可以固定，未给的部分写待确认；不能因允许异步就丢弃来源已明确的跨状态约束。

通知可按事件键归组，真实副作用不能被去重隐藏。幂等核对应保留全部真实流水和持仓变化，累计其实际效果，再与一次业务应产生的效果比较；不能先只保留一条同键流水再宣布未重复入账。

## 增量补漏

先建立已有点到规则/风险的映射，识别真缺口；修改错误预期与新增点分别记录。数量增加不是补漏价值，补充必须说明新增哪种业务判别能力。

不要把具有不同生效顺序或独立观察意义的点合并掉。重复 ID 要保留原位置，拟定新 ID 时提供映射并说明原因。

## 推荐验证层级

金额公式/状态不变量适合模型或单元层，真实竞争和恢复边界常需服务级可控事件，接口语义适合接口层，少量跨模块与用户可见结果适合端到端。按项目实际能力选择，不能假定已有注入接口、只读库或观测工具。

分层建议不等于为平台再建执行框架。当前任务交付测试设计，执行和脚本由既有平台或后续任务处理。
