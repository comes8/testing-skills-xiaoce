# 测试点输出与增量约定

默认用中文表格或分组清单，不强制 JSON 或固定列数。若用户要求平台格式，先核对字段与调用阶段，不能声称普通文档已兼容某个平台。

## 测试点语义

| 信息 | 最低要求 |
|---|---|
| ID 与目标 | 稳定 TP 编号，具体业务性质或要发现的风险 |
| 依据与范围 | 来源/规则/模型 ID、产品模式及必要版本；没有模型也可直接引用原始资料 |
| 条件与触发 | 必要初态、数据或等价类、动作/事件与决定结果的顺序 |
| 预期与就绪度 | 允许/禁止结果，固定判据与待确认子断言分开 |
| 核对方法 | 观察对象、关联键、公式/独立证据、时序或数据准备缺口 |
| 优先级与层级 | 按需要给建议等级、理由和合适验证层级，不能冒称项目已定级 |

完整操作步骤、请求体和自动化代码不属于本阶段默认产物。一个业务点可含支撑同一性质的多项观察，不强行把多对象一致性拆碎。共享一个 TP 的独立变体用子场景标签定位，分别记录条件和判据；不能用一个变体的证据代表全部。数值预期注明处理中或完成后的适用截面。

## 双维度状态

- **设计就绪度**：可设计 / 局部待确认 / 受阻。局部待确认应写清可固定的性质和未定分支。
- **执行准备**：已知可用 / 需准备 / 能力待核对；只依据输入说明，不把未执行记成通过。

材料明示不等于已批准，建议不等于产品规则；来源性质应可回查。规则明确但缺少测试环境能力，不能被误写成业务规则不明确。反之，环境能执行也不能替代预期依据。

## 覆盖映射

将关键需求/规则/不变量与 TP 关联，标记已有覆盖、局部待确认、缺失或本次不适用。允许一个点关联多个相互相关规则，也允许一个规则由多个不同风险点覆盖。

“有关联”不代表足够覆盖：检查每个独立约束和关键分支是否真的有判据。不要根据点数或分类齐全宣称完整覆盖，更不能伪造百分比。

## 增量输出

用户只要补充时，以差异为主：

- 新增：新 ID、覆盖什么缺口、依据、预期与核对方法。
- 修改：原 ID、原内容定位、变化及原因、受影响规则。
- 保留/复用：必要时说明已覆盖，不复制整份清单。
- 合并/废弃建议：保留原 ID 到存续点的映射，以及没有丢失的条件/证据。

重复 ID 用“原 ID＋序号/位置”准确定位；如果不同内容共用 ID，不能静默覆盖其中一条。未经要求不修改已有文件格式或平台数据。

## 待确认项与结论

问题关联到实际受阻 TP 和子断言；已有答案不重复提问。结论说明本批范围、关键覆盖、剩余缺口及准备条件，不能以“未决策略任一结果都算过”隐藏需求缺口。

本 Skill 自包含，可直接使用原始资料或现有测试点。无需依赖其他规划中的 Skill，也不会自动运行交易、压测或写入平台。
